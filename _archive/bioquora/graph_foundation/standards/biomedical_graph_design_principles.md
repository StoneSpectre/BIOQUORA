## The 8 Permanent Constitutional Rules of BioGraph

### Rule 1: Identity (Canonical Deduplication)
Every biomedical entity in the graph MUST possess exactly one canonical `bioq_id` and one primary authoritative CURIE (`preferred_id`). Duplicate nodes representing the same biological entity are strictly prohibited. External synonyms and secondary database IDs are stored in `aliases` and `external_ids`.

### Rule 2: Evidence (Zero-Unverified-Edges)
No relationship (`Edge`) may exist in the graph without an attached evidence envelope containing at least one verified publication reference (`PMID` / `DOI`), extraction confidence score (`[0.0, 1.0]`), and empirical context (`study_type`, `p_value`).

### Rule 3: Provenance (Immutable Cryptographic Lineage)
Every node and edge must store its exact origin pipeline, ingestion batch ID, publication timestamp, and cryptographic SHA-256 hash of the source text span.

### Rule 4: Ontology Grounding (Standardized Semantics)
Ad-hoc entity types are forbidden. Every node category and relationship predicate must map directly to standardized biomedical ontologies (OBO Foundry, EBI OLS, MONDO, DrugBank, UniProt, Reactome, GO).

### Rule 5: Versioning (Immutable Historical Graph Releases)
Updates to biomedical knowledge never overwrite history destructively. Any schema or factual revision generates a versioned snapshot (`v1.0.0-KG`), allowing precise reproduction of past scientific reasoning.

### Rule 6: Explainability (Traceable GraphRAG Paths)
Every multi-hop inference or drug repurposing hypothesis generated by BIOQUORA must emit a complete subgraph path trace (`Path = Node A -> Edge 1 -> Node B -> Edge 2 -> Node C`) accompanied by human-readable literature citations.

### Rule 7: Temporal Awareness (Knowledge Mutability Tracking)
Every node and edge tracks `created_at`, `discovered_at`, `updated_at`, and `status` (`ACTIVE`, `SUPERSEDED`, `DEPRECATED`), reflecting the evolving nature of clinical consensus.

### Rule 8: Extensibility (Zero-Redesign Schema Expansion)
The core schema is polymorphic and ontology-aware, allowing new node categories or specialized edge properties to be ingested without breaking existing queries or API contracts.
